# v1.5.0 — Full Design

**Status:** proposed
**Scope:** every piece discussed for v1.5.0 — web UI (foundation, job
submission/dashboard, browser-native JupyterLab/terminal, file manager),
multi-cluster support, and the three scaling/hardening fixes. This
supersedes the narrower `2026-08-04-v1.5.0-scaling-hardening-design.md`
spec by including everything, not just the hardening slice.

**How to read this doc:** each section is written to the same design bar —
architecture, components, data flow, testing — grounded against the real
current code, not aspirational. Sections 6–8 (scaling/hardening) carry
over unchanged from the earlier spec since they were already fully
designed and grounded. Sections 1–5 (web UI, multi-cluster) are new.

**One thing worth restating plainly**: this is a large bet. Sections 1–4
alone are a multi-month build that adds a new access surface, a new
security boundary (a web server + reverse proxy, versus just `sshd`), and
walks back the zero-external-infrastructure property that differentiated
this tool from Open OnDemand in the first place. Writing the full design
doesn't commit to building all of it at once — see §10 for a phasing
recommendation that lets §6–8 (and even §5) ship independently of the web
work ever landing.

## 1. Web UI foundation

### Architecture decision: FastAPI, reusing `slurmdeck/` as a shared service layer

The existing codebase already separates *mostly* cleanly into business
logic (`jobs.py`, `slurm.py`, `admin.py`, `files.py`, `validate.py`,
`launchspec.py`) and presentation (`menu.py`, `wizard.py`, `dashboard.py`,
`review.py` — Rich/questionary-specific). `launchspec.py` in particular is
already a pure, presentation-free module (`LaunchSpec`, `SIZES`, recent-file
lookup) — directly reusable by a web layer with zero changes. The plan is
**not** a rewrite of the backend: a new FastAPI application imports the same
`slurmdeck` package and calls the same functions the TUI already calls.
Some presentation-mixed modules (`dashboard.py`'s status computation,
`review.py`'s hub-building) need a light split — pull the "compute
current state as plain data" half out from the "render it as a Rich Panel"
half, so both the TUI and the web API can call the same data-producing
function and render it differently. This is a targeted refactor, not a
rewrite, and it's the same kind of split `launchspec.py` already
demonstrates works well here.

**Why FastAPI specifically**: Python (reuses everything above with no
FFI/rewrite), native async (relevant given what we just learned building
the audit daemon fix — slow I/O must not block other requests), built-in
WebSocket support for live updates (dashboard, log tailing), and Pydantic
validation matching this project's existing discipline around explicit,
tested validation (`validate.py`).

### Auth model: per-user process spawning, not a shared service account

This is the most important decision in the whole web section, and the
project's own existing trust model already answers it. Both the current
TUI (`ForceCommand` execs as the real logged-in user) and Open OnDemand
(Passenger spawns a backend process per authenticated user, running as
their real UID) independently arrive at the same principle: **never run
user work as a shared privileged account.** The web layer has to do the
same, or it regresses the tool's actual security model.

Concretely:
- A small privileged **login broker** (root-run, analogous in spirit to
  the existing audit daemon's SO_PEERCRED broker) accepts a login attempt
  (username + password, checked via PAM against the real Linux account —
  the same account created by `provision_user`/`slurm-deck-adduser` today),
  and on success forks a per-user backend worker process, dropping
  privileges to that user's real UID/GID before it does anything else.
- That worker process is what actually calls into `slurmdeck.jobs`,
  `slurmdeck.files`, etc. — so every filesystem read/write and every
  `sbatch`/`squeue` call happens as the real user, inheriting real POSIX
  permissions and real SLURM per-UID accounting, exactly like today's TUI.
  No new jail-bypass surface is introduced, because nothing new needed to
  be built to enforce the boundary — the OS already does it, same as now.
- The browser talks to a lightweight front-end process (session routing +
  static assets) which proxies each authenticated user's requests to
  *their* worker process. Session tokens are opaque, short-lived, and
  mapped server-side to the correct worker — never trusted client-side for
  authorization.
- This is more work than a single shared-backend design, but a
  shared-backend design would mean every filesystem/SLURM operation needs
  its own `sudo -u <user>` plumbing (more attack surface concentrated in
  one process holding broad privilege) instead of the OS enforcing it
  structurally. Given this project's whole audit-trail/jail design
  philosophy, the per-user-process model is the only one consistent with
  it.

### Relationship to the existing TUI

**Kept, not replaced.** The TUI remains the SSH-based access path (zero
extra attack surface for anyone who doesn't need a browser); the web UI is
an additional surface sharing the same backend modules. This also means
the web UI can ship incrementally, screen by screen, without ever breaking
the existing TUI users depend on today.

## 2. Web job submission & dashboard

- REST endpoints wrapping `launchspec.py` (already pure — reused directly)
  and the (split-out) job-building logic from `review.py`/`jobs.py`:
  `POST /api/jobs` (submit), `GET /api/jobs` (list, scoped to the
  authenticated user unless admin), `GET /api/jobs/{id}` (detail),
  `POST /api/jobs/{id}/cancel`.
- Live dashboard via WebSocket (`/ws/dashboard`): server pushes job-state
  and cluster-resource updates, reusing the split-out data half of
  `dashboard.py`'s `_merged_jobs`/`resource_status_line` (returning
  structured JSON instead of Rich markup strings — the web frontend does
  its own rendering).
- The review-hub concept carries over as a multi-step form: pick intent →
  pick script (jailed browser, reusing `files.py`'s existing jail logic) →
  editable summary before submit, mirroring the TUI's three-question-wide
  flow rather than a long form (the thing that already differentiates this
  tool's UX from a generic job-composer form).

## 3. Browser-native JupyterLab/terminal access

### Interactive-app proxying (no manual tunnel)

`connect.py` already does the hard part: it detects a job's readiness
marker (`.sd-ready`) and parses the node/port straight out of the job's own
stdout (never reconstructed). The web version reuses that exact detection,
then registers a reverse-proxy route (`/proxy/{job_id}/...` →
`http://{node}:{port}/...`) once the job is ready. Implemented as an
in-app streaming proxy (`httpx` inside the FastAPI app) rather than
dynamically-generated nginx config — simpler to manage per-job routes
without touching infrastructure config files; revisit only if proxy
latency proves to be a real problem in practice.

### In-browser terminal

A WebSocket-bridged pty: the per-user worker process spawns a real pty
running the user's shell (or the TUI itself, for users who want the
existing menu experience in a browser tab), streams bytes over the
WebSocket, and the frontend renders with `xterm.js`. Worth noting: this
session's own screenshot-capture tooling (`pexpect` + `pyte`, built to
generate the real README screenshots) is functionally the same
pty-bridging pattern, just captured to a file instead of streamed live —
directly relevant prior art from this project, not a new technique.

## 4. Web file manager

- Endpoints wrapping the existing jailed logic in `files.py`/`upload.py`
  (`in_user_browse_jail`, `in_user_upload_jail`) directly — these are
  already pure functions independent of Rich/questionary, so the web layer
  calls the same jail-checking code the TUI does today. No new jail logic,
  no new place for a path-traversal bug to hide.
- Browser file manager: list/upload/download/rename/delete, drag-and-drop
  upload, and an in-browser text editor (CodeMirror/Monaco) for small files
  — the same capability gap flagged earlier versus Open OnDemand.

## 5. Multi-cluster support

- Generalize `deploy/site.env` (one cluster's config) into a directory of
  named cluster profiles — `deploy/clusters.d/<name>.env` — mirroring Open
  OnDemand's `clusters.d/*.yml` pattern closely, since it already solves
  this exact problem well.
- `config.py`'s `load_config()` gains a `cluster` selector (env var or
  explicit argument) to pick which profile to load, instead of assuming
  the single global config it does today.
- TUI gains a cluster-picker step before the Main Menu, shown only when
  more than one cluster is configured (zero UX change for single-cluster
  sites). The web UI (§1–4, if built) gets the same picker.
- The part needing the most care: `jobs.py`/`slurm.py`'s subprocess calls
  currently assume they're already running *on* the right login node. True
  multi-cluster means a single running process might need to submit to a
  **different** cluster's scheduler — which means SSHing out to that
  cluster's login node for scheduler commands, the same cross-node SSH
  pattern already used by `slurm-deck-adduser`/the audit daemon's
  cross-node calls, not a new mechanism.
- Can ship entirely independently of §1–4 — this is a `config.py` +
  `jobs.py`/`slurm.py` change plus a TUI picker screen, no web UI required.

## 6. Audit daemon concurrency

*(unchanged from the earlier scaling/hardening spec — included here for
completeness.)*

### Problem (verified against the live code)

`deploy/audit_daemon.py`'s `main()` runs a single-threaded `select()` loop
that calls `_handle_connection()` inline — one request fully completes
before the next is even accepted. Two verb handlers block that single
thread on real I/O: `mail.send` → `_resend_send()`'s
`urllib.request.urlopen(..., timeout=20)` (up to 20s), and
`service.status` → `systemctl`/`journalctl` subprocess calls (up to 15s
combined). This is a live bug today: one slow Resend response freezes
login, job submission, file access, and audit logging for every other user
for up to 20 seconds.

### Design

Bounded `ThreadPoolExecutor(max_workers=8)` instead of inline handling;
each worker opens its own short-lived SQLite connections instead of
sharing `audit_conn`/`users_conn` across threads; `PRAGMA
journal_mode=WAL` on both DB files at startup so SQLite's native locking
handles concurrent reads/one-writer safely with no custom locking code.
Callers see no behavior change — the triggering client still waits for its
own real result, only other clients stop being blocked by it.

### Testing

New regression test: real daemon against a tmp Unix socket, slow fake
`mail.send` from one client thread, assert a concurrent fast
`users.email_for` call from another client completes first. Existing
`test_daemon_verbs.py` unaffected (handler logic untouched).

## 7. Per-user disk quotas

*(unchanged from the earlier spec.)*

### Problem (verified against the live filesystem)

`/shared` is backed by **ext4** (not XFS — the original "XFS project
quotas" note was wrong for this deployment), no quota tooling installed.
Kernel-level quotas would need a live remount (`prjquota`) or reboot.
Also found: `admin.disk_usage_by_user()` only scans `/shared/jobs/<user>`,
missing `/shared/users/<user>` — undercounts every user's real usage today.

### Design

Application-level, not kernel-level. Extend `disk_usage_by_user()` to sum
both `users/` and `jobs/` subdirs. New periodic timer (mirroring the
existing `slurm-deck-pod-notify` pattern), every 15 min, caches per-user
usage into `users.db` (`quota_usage_bytes`, `quota_checked_at`).
`upload.py`'s `run_upload()` checks the cached value against a `quota_gb`
column (site-wide `DEFAULT_USER_QUOTA_GB` default, empty = unlimited) before
accepting new uploads. Not enforced at job-submit time in v1.5.0 (job
output growing mid-run is a harder problem, explicitly deferred). Admin
panel's disk-usage screen extended to show quota + percent-used; new "Set
user quota" action for overrides.

### Testing

Unit tests for the extended usage function against a tmp tree covering
both subdirs; unit tests for the upload-time check (under/at/over quota).

## 8. Bulk user provisioning

*(unchanged from the earlier spec.)*

### Design

New admin panel item, CSV-driven (`username,email,full_name,role`), picked
via the existing jailed file browser. Validates every row up front, shows
a preview (valid/invalid counts + reasons) with one confirmation
checkpoint, then provisions row by row via the **existing**
`admin.provision_user()` unchanged — no new provisioning logic, just a
loop and a summary report. Auto-generates a random password per row (can't
prompt for N passwords), so the existing welcome-email path fires exactly
as it does for single-user provisioning today. Does not abort on the first
failure — collects per-row results, reports a final summary.

### Testing

Unit tests for CSV parsing/validation (malformed rows, duplicate
usernames, invalid roles) against a faked `provision_user` (no real
account creation in tests); a test confirming one failure doesn't abort
the remaining rows.

## 9. Testing strategy overview

- §6–8 are unit-testable within the existing pytest suite with no new
  infrastructure — same patterns already used throughout this codebase
  (fakes/mocks for subprocess and network calls, in-memory SQLite for
  daemon-handler tests).
- §1–5 need a new test tier: FastAPI's own `TestClient` for the REST/
  WebSocket endpoints (fast, no real browser needed), plus the *existing*
  `pexpect`+`pyte` pty-bridging technique from this session's screenshot
  tooling as a starting point for testing the in-browser terminal's pty
  bridge specifically (it already proves the pattern works end-to-end
  against this exact codebase).
- No production cluster testing for §1–5 beyond what's already this
  project's standard: verify against demo mode first, then the real
  cluster, same discipline used for every feature so far.

## 10. Implementation order / phasing recommendation

Not everything here needs to ship together, and most of it doesn't depend
on the rest:

1. **§6 Audit daemon concurrency** — ship first, alone. It's a correctness
   fix for a live bug, fully independent of everything else, highest
   urgency.
2. **§7 Disk quotas** — second; benefits from §6 being stable (the quota
   timer talks to the same daemon/DB), otherwise independent.
3. **§8 Bulk provisioning** — smallest, lowest urgency, slots in whenever.
4. **§5 Multi-cluster** — independent of §1–4 entirely (no web UI
   required). Real, scoped work; can ship on the TUI alone.
5. **§1–4 Web UI** — the large bet. Recommend treating this as its own
   gated decision after 1–4 above ship, informed by whether a concrete
   driver has shown up by then (see the framing note at the top of this
   doc) — not committed to a date here.

Each numbered item still gets its own implementation plan (per
`superpowers:writing-plans`) and TDD cycle when it's actually built — this
spec documents the full designed shape of v1.5.0, not a single
undifferentiated implementation task.

## 11. Open questions / risks worth flagging now

- **§1 auth broker** is the single highest-risk new component in this
  whole document — a root-privileged process that forks per-user workers
  is exactly the kind of code that needs the most scrutiny (mirrors the
  audit daemon's own SO_PEERCRED care, but with higher stakes since it's
  actively dropping privileges rather than just checking an identity).
  Deserves its own focused security review before implementation, not
  just a general one.
- **§3 in-browser terminal** raises the same audit-trail question the
  earlier Slurm-Deck-vs-OOD comparison flagged for OOD's own in-browser
  terminal: a terminal is inherently less auditable than the structured
  TUI menu.
  Worth deciding up front whether browser-terminal sessions get the same
  audit logging rigor as everything else, or are explicitly scoped as a
  less-audited escape hatch (matching the existing `--shell-user` role's
  own documented tradeoff).
- **§5 multi-cluster's cross-node SSH submission path** needs its own
  credential/connectivity design (which account submits to a remote
  cluster, how that SSH access is provisioned) before implementation —
  flagged here, not designed yet.
