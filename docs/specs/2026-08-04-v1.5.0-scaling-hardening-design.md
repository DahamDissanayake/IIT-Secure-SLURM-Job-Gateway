# v1.5.0 — Scaling & Hardening Design

**Status:** proposed
**Scope:** three independent pieces, bundled into one release: audit daemon
concurrency, per-user disk quotas, bulk user provisioning. None require the
web-UI/multi-cluster work discussed separately — all three ship on top of
the current SSH-TUI architecture as-is.

**Explicitly out of scope for this spec:** the full web-based UI migration
and multi-cluster support. Both were flagged as separate, much larger
initiatives during brainstorming and deliberately deferred — see the
"why not now" note at the end of this doc.

---

## 1. Audit daemon concurrency

### Problem (verified against the live code, not assumed)

`deploy/audit_daemon.py`'s `main()` runs a single-threaded `select()` loop
that calls `_handle_connection()` **inline** for every accepted connection —
one request fully completes before the next is even accepted, despite a
`listen(16)` backlog.

Two verb handlers do blocking I/O on that same single thread:

- `mail.send` → `_resend_send()` — `urllib.request.urlopen(..., timeout=20)`,
  a live call to Resend's API. Up to **20s** blocking.
- `service.status` (admin "Service health") → `systemctl is-active` +
  `journalctl`, up to **15s** combined blocking.

This is a live bug today, not just a future scaling risk: one slow Resend
response during a welcome email freezes login, job submission, file access,
and audit logging for **every other user** for up to 20 seconds, because
they all funnel through the same accept loop.

### Design: bounded thread pool + per-thread SQLite connections + WAL mode

- Replace the inline `_handle_connection(conn_sock, audit_conn, users_conn)`
  call in `main()`'s accept loop with submission to a
  `concurrent.futures.ThreadPoolExecutor(max_workers=8)` (bounded — no
  unbounded thread-per-connection growth under a burst).
- `_handle_connection` stops receiving shared `audit_conn`/`users_conn`
  arguments; each worker thread opens its own short-lived SQLite connections
  (`sqlite3.connect(str(DB_PATH))`, `sqlite3.connect(str(USERS_DB))`) for the
  duration of that one request, closed on completion. Simpler and safer than
  sharing connection objects across threads.
- Enable `PRAGMA journal_mode=WAL` on both `audit.db` and `users.db` at
  daemon startup (idempotent — safe to run every start, no-op if already
  WAL). WAL mode is what makes this safe without any custom locking code:
  it natively allows concurrent readers plus one writer, which is exactly
  the access pattern here (many fast reads, occasional fast writes, two rare
  slow writes for mail/service-status).
- **Callers see no behavior change.** The client that triggered a slow mail
  send still waits and gets the real success/failure result — worker
  threads don't change per-request semantics, they only stop one slow
  request from blocking every other connection.
- 8 workers is a starting number, not a tuned constant — cheap to bump via a
  module-level constant if real usage shows contention; not exposed as a
  site.env setting in v1.5.0 (YAGNI until there's evidence it needs to be
  configurable per-site).

### Testing

- Existing `tests/test_daemon_verbs.py` calls handler functions directly
  against in-memory SQLite — unaffected by this change (handlers' logic is
  untouched; only how `main()` dispatches to them changes).
- New test: spin up the real daemon against a Unix socket in a tmp dir, fire
  a slow fake `mail.send` (mock `_resend_send` with a `time.sleep`) from one
  client thread, assert a concurrent second client's fast `users.email_for`
  call completes well before the slow one does — this is the regression
  test for the actual bug (single-threaded blocking), not just a unit test
  of the handler logic.
- Verify WAL mode is actually active post-startup
  (`PRAGMA journal_mode` returns `wal`) as a startup self-check, logged at
  daemon start.

### Rollout

Same pattern already used throughout this project for live daemon changes:
deploy the new `audit_daemon.py`, `systemctl restart slurm-deck-audit`,
verify PID actually changed (already how `redeploy-slurm-deck.sh` checks
every restart). WAL mode's `-wal`/`-shm` side files appear next to the
existing `.db` files automatically — no migration step, no downtime beyond
the restart itself.

## 2. Per-user disk quotas

### Problem (verified against the live filesystem, not assumed)

The original "add disk quotas" note (carried over from early project
history) assumed XFS project quotas. **The actual filesystem backing
`/shared` is ext4** (`/dev/nvme0n1p1`, mounted `rw,relatime`, no quota
options), and no quota tooling (`xfs_quota`, `repquota`) is installed.
Kernel-level project quotas on ext4 are possible but require remounting
with `prjquota` (or a reboot) plus `quotacheck` — real live-filesystem risk
for a feature that doesn't need kernel enforcement to be useful.

Also found while grounding this: the existing admin panel feature
`admin.disk_usage_by_user()` only scans `/shared/jobs/<user>` — it misses
`/shared/users/<user>` (uploaded data, models, scripts) entirely, so even
today's usage view undercounts every user's real footprint.

### Design: application-level, periodically-cached usage + upload-time enforcement

- **Extend, don't replace, `disk_usage_by_user()`**: change it to sum both
  `NFS_ROOT/users/<user>` and `NFS_ROOT/jobs/<user>` per user (fixing the
  undercount as a side effect), returning combined bytes.
- **New periodic cache**, mirroring the existing `slurm-deck-pod-notify`
  timer pattern already in this codebase (`deploy/slurm-deck-quota-check` +
  matching `.service`/`.timer`, every 15 min): runs the (extended) disk-usage
  scan for every user, writes results to a small table in `users.db`
  (`quota_usage_bytes`, `quota_checked_at` columns on the `users` row).
  Scanning on a timer instead of on every request avoids a `du`-cost
  recursive filesystem walk on every single upload/job-submit — bounded
  staleness (≤15 min) is an acceptable tradeoff for a soft quota, not a
  hard security boundary.
- **Enforcement point**: `upload.py`'s `run_upload()` checks the *cached*
  usage against the user's quota (`quota_gb` column, defaults to
  `DEFAULT_USER_QUOTA_GB` from site.env if unset) before accepting a new
  upload — refuses with a clear message if it would exceed. This is a fast,
  cheap check (one DB read), not a live filesystem scan.
- **Not enforced at job-submit time in v1.5.0** — job output growing
  unbounded mid-run is a harder problem (would need to kill a running job
  over quota, out of scope here) and the periodic check + upload gate cover
  the two places users actually add new data. Flagged as a known limit, not
  silently ignored.
- **Admin visibility**: extend the existing "Disk usage by user" admin
  screen to show quota + percent-used per row, using the same cached data.
  New admin action "Set user quota" (updates the `quota_gb` override column)
  for exceptions.
- **Default quota**: `DEFAULT_USER_QUOTA_GB` in site.env, no default value
  shipped (empty = unlimited, matching this project's existing "don't
  silently invent a constraint nobody asked for" pattern) — a site turns
  this on by setting a number.

### Testing

- Unit tests for the extended `disk_usage_by_user()` against a tmp
  directory tree covering both `users/` and `jobs/` subdirs.
- Unit tests for the upload-time quota check (mocked cached-usage values,
  under/at/over quota cases).
- `deploy/slurm-deck-quota-check` tested the same way
  `slurm-deck-pod-notify`'s script is tested today — logic covered via
  direct function calls, not the timer itself.

## 3. Bulk user provisioning

### Design: CSV-driven, wraps the existing `provision_user()`

- New admin panel item "Bulk provision users" (User Management section,
  alongside the existing single-user "Provision user").
- Input: a CSV path, picked via the same jailed file browser already used
  elsewhere in the admin panel. Columns: `username,email,full_name,role`
  (role optional, defaults to `tool`).
- Processing: read and validate every row up front (username format, email
  format, role in `admin`/`tool`/`shell`) before provisioning anything —
  show the admin a preview ("12 valid, 2 invalid: row 4 bad username, row 9
  missing email") and a single confirmation checkpoint, consistent with this
  project's confirm-before-mutating-action convention.
- Provisions **one row at a time**, calling the existing
  `admin.provision_user()` unchanged — no new provisioning logic, this
  purely adds a loop and a summary report around what already exists. Each
  row gets its own randomly-generated initial password (can't reasonably
  prompt for 150 passwords), so every successfully-provisioned user gets the
  existing welcome email with credentials, unchanged from today's single-user
  path.
- **Does not stop on first failure** — one duplicate username or SSH hiccup
  shouldn't block the other 149 rows. Collects a per-row result and prints a
  final summary (succeeded / failed + reason per failure), matching how
  `provision_user()` already returns `(ok, msg)` per call.

### Testing

- Unit tests for CSV parsing/validation (malformed rows, duplicate
  usernames within the same file, invalid roles) using a fake
  `provision_user` so no real account creation happens in tests.
- Unit test confirming partial failure doesn't abort the remaining rows.

## Implementation order

1. Audit daemon concurrency — ships alone first; it's a correctness fix for
   a bug that exists right now, independent of the other two, highest
   urgency.
2. Disk quotas — second; touches live storage/admin UI, benefits from the
   daemon fix being stable first (quota-check timer talks to the same
   daemon/DB).
3. Bulk provisioning — last; smallest, lowest urgency, easiest to slot in
   whenever.

Each still gets its own implementation-plan/TDD cycle (per
`superpowers:writing-plans`) — this spec covers all three because they're
being designed together for one release, not because they should be built
as a single undifferentiated change.

## Why not the full web UI / multi-cluster work in this release

Flagged during brainstorming and deliberately deferred: both are
multi-month efforts that change what kind of product this is (new access
surface, new security boundary, walks back the zero-external-infrastructure
property that differentiates this tool from Open OnDemand). Worth a
dedicated go/no-go conversation grounded in a concrete driver (a real need
for browser-only access, a less technical user population, an institutional
requirement) before committing design time to them — not something to fold
into a hardening release by default.
